# Seamless_CAD Kernel Protocol Notes

This file records the protocol used by `reference/CAD_8_1_5_1/core_bridge.py` so a Rust replacement for `cad_server.exe` can be built without rewriting the Blender UI first.

> **これは「あるべき仕様」であって、`zenith_server` の現状ではありません。**
> `zenith_server` が実装しているのは `create_stack` と `delete_stack` だけで、
> ここに載っている他の動作は**名前を挙げて断ります**（空のメッシュや 0 の
> 計測値を成功として返すのをやめたため。[`HANDOVER.md`](HANDOVER.md) 4-41）。
> Blender との連携は、いまのところ `zenith_py` のインプロセス経路のほうが
> 先に動いています。

## Transport

- Host: `127.0.0.1`
- Port: `8080`
- Normal request framing:
  - client sends `<u32 little-endian message_len>`
  - client sends `message_len` bytes of UTF-8 JSON
- `update` request framing with geometry stack payload:
  - client sends `<u32 little-endian total_len>`
  - payload starts with `<u32 little-endian json_len>`
  - then `json_len` bytes of UTF-8 JSON
  - then raw `binary_payload`

## Response Status

The server always starts a response with one status byte:

- `1`: success
- `2`: empty/no-op response used by the client as `None`
- other: error; followed by `<u32 err_len>` and UTF-8 error message

## JSON Actions

### `create_stack`

Request:

```json
{"action":"create_stack"}
```

Success response:

- status `1`
- `<i64 little-endian stack_ptr>`

### `delete_stack`

Request:

```json
{"action":"delete_stack","stack_ptr":123}
```

Success response:

- status `1`

### `update`

Request JSON fields observed:

```json
{
  "action": "update",
  "stack_ptr": 123,
  "fast_mode": false,
  "f_radius": 0.0,
  "f_deflection": 0.1,
  "f_angular_deflection": 0.008726646,
  "f_lineage_list": [],
  "json_str": "",
  "include_mesh": true
}
```

The request also carries `binary_payload`, generated by `serialize_primitives(stack_data)`.

Success response:

1. status `1`
2. five lengths: `<u32 edge_points_len, u32 edge_counts_len, u32 mesh_verts_len, u32 mesh_tris_len, u32 mesh_tri_counts_len>`
3. metadata JSON length: `<u32 meta_json_len>`
4. UTF-8 JSON metadata
5. if `meta.use_mmap` is false, raw arrays:
   - `edge_points`: `float32`
   - `edge_counts`: `int32`
   - `mesh_verts`: `float32`
   - `mesh_tris`: `int32`
   - `mesh_tri_counts`: `int32`
6. if `meta.use_mmap` is true, arrays are read from the shared memory file using `meta.mmap_offsets`

Metadata fields consumed by Python:

```json
{
  "use_mmap": false,
  "mmap_offsets": [0, 0, 0, 0, 0],
  "edge_lineages": [],
  "mesh_face_ids": [],
  "perf_bool": 0,
  "perf_edge": 0,
  "perf_mesh": 0,
  "perf_prim": 0,
  "perf_bool_main": 0,
  "perf_bool_modifier": 0,
  "perf_extrema": 0,
  "perf_unify": 0,
  "perf_resume_restore": 0,
  "perf_modifier_target_assign": 0,
  "perf_modifier_apply": 0,
  "perf_modifier_recluster": 0,
  "perf_fillet_setup": 0,
  "perf_fillet_target_resolve": 0,
  "perf_fillet_add": 0,
  "perf_fillet_build": 0,
  "perf_fillet_history": 0,
  "perf_fillet_added_edges": 0,
  "perf_fillet_contours": 0
}
```

### `generate_mesh`

Request:

```json
{
  "action": "generate_mesh",
  "stack_ptr": 123,
  "deflection": 0.1,
  "angular_deflection": 0.008726646
}
```

Success response:

1. status `1`
2. three lengths: `<u32 mesh_verts_len, u32 mesh_tris_len, u32 mesh_tri_counts_len>`
3. metadata JSON length: `<u32 meta_json_len>`
4. metadata JSON with `face_ids`
5. arrays:
   - `mesh_verts`: `float32`
   - `mesh_tris`: `int32`
   - `mesh_tri_counts`: `int32`

### Import/export actions

Actions:

- `import_step`
- `import_svg`
- `export_step`
- `export_stack_to_step`
- `export_parts_to_step`
- `export_stack_to_stl`
- `export_stack_to_iges`

`import_step` and `import_svg` return status `1`, `<u32 json_len>`, then JSON data.

Export actions return only status `1` on success.

### Measurement

`measure_stack` returns status `1` plus 11 `f64` values:

1. volume
2. surface area
3. center of mass x
4. center of mass y
5. center of mass z
6. bbox min x
7. bbox min y
8. bbox min z
9. bbox max x
10. bbox max y
11. bbox max z

`measure_entity` returns status `1` plus 10 `f64` values:

1. type flag or validity value
2. length or area
3. radius
4. shape kind code
5. center x
6. center y
7. center z
8. normal x
9. normal y
10. normal z

Entity kind codes expected by Python:

- edge: `0 Line`, `1 Circle`, `2 Ellipse`, `3 Curve`
- face: `0 Plane`, `1 Cylinder`, `2 Cone`, `3 Sphere`, `4 Torus`, `5 Surface`

### Viewport and previews

Actions:

- `render_viewport`
- `render_viewport_sdf`
- `csg_preview_begin`
- `csg_preview_update`
- `csg_preview_end`
- `solve_sketch`

These can be implemented after the first stack/update/mesh vertical slice. `csg_preview_update` has a custom compact binary response:

- status `1`
- `<u32 points_len, u32 counts_len>`
- `points` as `float32`
- `counts` as `int32`
- optional ghost payload if requested

## Binary Pick Protocol

Picking uses a non-JSON message after the outer `<u32 message_len>` frame.

Observed op codes:

- `1`: `pick_edge`
- `2`: `pick_face`
- `3`: `pick_vertex_from_stack`
- `4`: `pick_midpoint_from_stack`
- `5`: `pick_face_from_stack`
- `6`: `pick_edge_from_stack`

Message without stack index:

```text
<u8 op_code>
<i64 stack_ptr>
<f32 origin_x, origin_y, origin_z>
<f32 dir_x, dir_y, dir_z>
<f32 tolerance>
```

Message with stack index:

```text
<u8 op_code>
<i64 stack_ptr>
<i32 stack_idx>
<f32 origin_x, origin_y, origin_z>
<f32 dir_x, dir_y, dir_z>
<f32 tolerance>
```

The Python reader expects:

1. status `1`
2. `<u32 result_len>`
3. result payload containing lineage string and float data

The exact result payload still needs to be completed from `_pick_common`.

## Primitive Binary Payload

`update` serializes a stack as:

```text
<u32 primitive_count>
primitive[0]
primitive[1]
...
```

Each primitive packs:

1. Eleven UTF-8 strings, each as `<u16 len> + bytes`:
   - `type`
   - `operation`
   - `uuid`
   - `reference_lineage`
   - `target_uuid`
   - `pattern_axis`
   - `top_shape`
   - `bot_shape`
   - `sweep_path_uuid`
   - `sweep_profile_uuid`
   - `sweep_frame_mode`
2. Thirteen `f64` transform values:
   - location xyz
   - Euler rotation xyz
   - size xyz
   - quaternion xyzw
3. Two bool bytes:
   - `fill_closed`
   - `use_pipe`
4. Scalars matching Python's struct format:
   - radius
   - pipe_radius
   - angle_start
   - angle_end
   - extrude_height
   - radius2
   - minor_radius
   - sides
   - module
   - pressure_angle
   - count
   - distance
   - sweep_roll_degrees
5. `target_lineages`: `<u16 count>`, then strings as `<u16 len> + bytes`
6. `loft_uuids`: `<u16 count>`, then strings as `<u16 len> + bytes`
7. `points`: `<u32 count>`, then `[x, y, z, use_fillet]` as four `f64`
8. `segments`: `<u32 count>`, then segment records
9. `edge_radii`: `<u32 count>`, then string token and `f64 radius`

The Rust server should implement a versioned parser for this format and reject short/truncated payloads with explicit errors.
